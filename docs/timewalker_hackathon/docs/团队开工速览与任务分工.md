## 我们统一的三个决定

**第一，故事模式是产品的独特价值，不弱化。** 保留已完成的豫园家书、上海天文馆深空讯号双样板与当前 Creative Studio；不重新开发故事引擎，不把广告推荐塞进主线剧情。

**第二，新增独立路线打卡模式（Trail）。** 从已有的豫园节点做一条四站主题探索线路。游客无需 GPS 即可按顺序打卡、收集印章、获得纪念卡；客服/运营人员可以编排地点顺序、站点说明和示例推荐内容，并把真实可打开的链接交给游客。

**第三，不证明真实收入，只展示可兑现商业价值的系统能力。** 现场可展示运营路线发布、可见推荐位和真实的浏览器事件。没有商户合作时标“演示推荐”；没有订单数据时不做假佣金/ROI 面板。

## 演示交付边界

完成 3 个游客入口（豫园故事、天文馆故事、豫园四站打卡）、1 个运营创作入口（路线编辑器 + 已有 Creative Studio）、1 套共用目的地数据和一个故事完成后进入打卡的联动。必须运行在真实的 Web 浏览器中。商业闭环不等于支付系统上线；故事和打卡之间互相推荐但互不依赖。

| 工作线 | 今天第一项 | 第一个可合并成果 | 后续任务 |
|---|---|---|---|

| B 游客 Trail | 在 A 契约基础上做打卡页面 | 四站手动确认、刷新恢复、完成卡 | 推荐卡、事件记录、故事→路线入口 |

| 日期 | 保底验收 |

| D5 | 三份体验+运营配置+Studio 预制成果五分钟串讲；Build/Lint/Node 测试与浏览器冒烟、真机回归 |

**如果时间缩减**：保住故事双样板与游客 Trail 闭环；运营配置可以暂时由开发者编辑 JSON，但不能自称“客服可发布”。先砍报表、第二条 Trail、复杂积分，再考虑缩减推荐位。

## 今晚必须确认的四件事

1. 是否把 Trail 作为独立 `/trail/:id` 入口？建议是；不重构 `/experience/:id`。
2. 运营发布是否仅需开发态静态写文件 + JSON 导出？建议是；不做生产级账号权限。
3. 商业推荐是否只是“可配置演示卡 + 点击事件”，无真实商户？建议是；如果有真实合作，单独核对目标链接。
4. AI 是否首先完成真实凭据联调、把成功产物导入现有 Studio？建议是；Deep Agents 暂时 P2。
